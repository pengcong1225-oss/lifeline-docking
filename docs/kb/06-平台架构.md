# 平台架构

## 定位

新平台（本项目 `lifeline-docking`）是**数据上收开放平台**，用来逐步替换老平台。
过渡期核心约束只有一条：

> **调用者只替换接口地址。** 继续使用老平台分配的 `accessKey/secretKey`、原请求路径、
> 原请求字段、原调用方式，不改鉴权代码、不改业务代码。

## 两条独立的迁移线

| 迁移线 | 第一天的状态 | 终态 |
| --- | --- | --- |
| **鉴权迁移** | 新平台独立对外验签、签发自己的令牌；内部访问老平台时仍用该调用者的老凭证取老令牌 | 不再需要老平台令牌 |
| **业务迁移** | 老平台是业务成功判定方；新平台逐类实现、影子比对、切换 | 新平台自行处理全部业务 |

不要混淆：鉴权从第一天就切到新平台，业务则是逐类切换的。

## 数据流

```text
① 登记（一次性）
   企业 → 提交老平台 accessKey/secretKey → AES-256-GCM 加密入库

② 取令牌
   调用者 → POST /data-docking-api/token
          → 新平台按兼容规则验签
          → 签发【新平台自己的】令牌，老平台令牌不返回

③ 推数据
   调用者 → POST /data-docking-api/execute/api  (Bearer 新令牌)
          → 验令牌、识别调用者
          → 可靠留存原始请求（失败则绝不转发）
          → 数据项按 lsh 判重入库
          → 按 apiCmd + tag + operationType 路由
              ├─ 已接管：新平台自行处理
              └─ 未接管：用该调用者老凭证取老令牌 → 同步转发老平台
                        老平台 code=0 才算成功
```

## 令牌的双层设计

```text
调用者 ──新平台令牌──> 新平台 ──老平台令牌──> 老平台
         (对外签发)              (内部获取，绝不外泄)
```

- **新平台令牌**：新平台自己签发，调用者用它访问新平台。
- **老平台令牌**：新平台用调用者的老凭证在内部换取，仅用于转发，**不返回给调用者**。

两者**不要求互认**，调用者也不需要维护两套令牌。

老平台业务接口要求 `Authorization: Bearer <token>`，所以「用调用者原凭证转发」
在技术上仍然包含内部获取老令牌 —— 不能把 `accessKey/secretKey` 直接当业务接口的令牌用。

## 请求状态机

| 状态 | 含义 | 对调用者的响应 |
| --- | --- | --- |
| `RECEIVED` | 已可靠留存，尚未转发 | — |
| `ACCEPTED_OLD` | 老平台返回 `code=0` | 业务 `code=0`（HTTP 200） |
| `REJECTED_OLD` | 老平台返回非零业务码 | 业务 `code=1`（HTTP 200） |
| `REJECTED_LOCAL` | 新平台自身拒绝（报文非法、路由缺字段、留存失败） | 业务 `code=1`（HTTP 400） |
| `UNKNOWN` | 老平台超时或断线，**结果未知** | 业务 `code=1`（**HTTP 502**） |

### 为什么把 UNKNOWN 单独拎出来

老平台超时或断线时，数据**可能已经写入老平台**，也可能没有。此时：

- **不能报成功** —— 调用者会以为数据已接收；
- **不能报失败让调用者盲目重推** —— 可能造成重复数据；
- **不能自动重放** —— 老平台幂等性尚未验证。

所以对外明确返回 502 + `code=1`，语义是「未确认，请人工核对」。
这是第一版**刻意**不做自动重试的原因。

## 逐类接管

`RouteRegistry` 维护「已由新平台接管」的路由键集合，第一版**为空**：
所有业务都转发老平台，由老平台判定成功。

切换某类业务的判断依据（缺一不可）：

1. 字段含义与必填规则已逐字段核对；
2. 成功/失败判定与老平台一致；
3. 重复提交、流水号冲突行为已确认；
4. 历史数据迁移与对账方案就绪；
5. 有可回退的开关（`RouteRegistry` 支持 `rollback`）。

试点建议：先挑**有明确唯一键、数据量适中、依赖少**的类别；
实时监测和带更新/删除顺序的类别后移。

## 安全边界

| 边界 | 做法 |
| --- | --- |
| 密钥存储 | `secretKey` 只用 AES-256-GCM 密文入库，明文只在签名瞬间存在于内存 |
| 密钥外泄 | 接口与日志只回显尾号（`****0001`） |
| 响应时序 | 签名比对使用恒定时间比较，避免侧信道泄露 |
| 结果未知 | 不伪装成功、不自动重放（见上） |
| 调试入口 | `lifeline.debug.enabled` 可关闭；生产必须关闭 |
| 管理接口 | `/admin/**` 当前**无鉴权**，生产前必须补上 |

## 部署形态

单体 Spring Boot 应用，无外部中间件依赖：

- MySQL 8（凭证、留存、数据项）
- 内嵌 Tomcat 提供对外接口、管理接口与知识库/调试页面
- 老平台令牌缓存与自签令牌目前在应用内存中（重启失效），生产建议换成 Redis 或数据库
