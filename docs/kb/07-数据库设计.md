# 数据库设计

数据库：MySQL 8，库名 `lifeline_docking`（首次启动由连接参数 `createDatabaseIfNotExist=true` 自动创建）。
建表脚本：`src/main/resources/schema.sql`，应用启动时由 `spring.sql.init` 执行，全部 `CREATE TABLE IF NOT EXISTS`，可重复运行。

## 三张表

```text
docking_caller_credential   企业登记的老凭证（密钥密文）
        │ accessKey
        ▼
docking_request_record      每次业务请求的留存信封（原始报文 + 状态 + 老平台响应）
        │ record_id
        ▼
docking_data_item           逐条业务数据项（判重、可查询）
```

## 1. `docking_caller_credential` —— 调用者凭证

| 字段 | 说明 |
| --- | --- |
| `access_key` | 老平台分配的 accessKey，**唯一键** |
| `secret_cipher` | secretKey 密文：`Base64(iv(12) \|\| ciphertext+tag)`，AES-256-GCM |
| `secret_hint` | 密钥尾号（如 `****0001`），仅用于人工识别，**不可回推密钥** |
| `company_name` / `contact` | 企业信息，便于运营识别 |
| `enabled` | `1`=启用 `0`=停用；停用后无法取令牌 |
| `verified_at` / `verify_message` | 最近一次向老平台验证凭证的结果 |

**设计要点**

- 只存密文。任何接口响应、日志、工单都不出现明文或密文。
- 主密钥来自 `LIFELINE_MASTER_KEY`；**更换或丢失主密钥会导致已登记密钥全部无法解密**。
- 更新凭证时 `accessKey` 不允许改（接口层面已限制），避免与已发放令牌的归属错位。

## 2. `docking_request_record` —— 请求留存

| 字段 | 说明 |
| --- | --- |
| `record_id` | 留存 ID（UUID），主键 |
| `access_key` | 调用者 |
| `api_cmd` / `tag` / `operation_type` | 路由键三要素 |
| `data_count` | 报文里 `data[]` 的条数 |
| `stored_count` | 实际入库条数 |
| `duplicate_count` | 因 `lsh` 重复被跳过（未覆盖）的条数 |
| `raw_body` | **原始请求体，原样保存** |
| `status` | 见[状态机](06-平台架构.md#请求状态机) |
| `message` | 处理说明 |
| `old_platform_code` | 老平台业务码；`NULL` 表示未取得（转发失败或未转发） |
| `old_response` | 老平台原始响应，排障时最关键的一列 |
| `source` | `API`=调用者推送，`DEBUG`=调试台 |
| `received_at` / `forwarded_at` | 接收与转发完成时间 |

**设计要点**

- **先留存再转发**。留存与数据项入库在**同一事务**内完成（`RecordPersister`）；
  留存失败直接返回失败，绝不转发。
- 保留 `raw_body` 原文而不只存解析结果，便于事后对账与复现。
- 索引：`received_at`（按时间查）、`(api_cmd, tag, operation_type)`（按业务查）、
  `status`（按状态筛）、`access_key`（按调用者查）。

## 3. `docking_data_item` —— 上收数据项

| 字段 | 说明 |
| --- | --- |
| `record_id` | 所属留存记录 |
| `api_cmd` / `tag` / `operation_type` | 冗余存一份，便于脱离信封独立查询 |
| `item_index` | 在 `data[]` 中的原始下标 |
| `lsh` | 流水号，**可空** |
| `payload` | 原始数据项 JSON |

### 判重策略

```sql
UNIQUE KEY uk_tag_lsh (tag, lsh)
```

- 源文档要求「按流水号做唯一校验」，所以对 `(tag, lsh)` 建唯一键。
- `lsh` 允许 `NULL`：第三方巡检族的接口没有 `lsh`，
  MySQL 唯一键允许多个 `NULL`，因此这些接口的数据不会被误判重复。
- 重复时**跳过插入并计数**（`duplicate_count`），**不覆盖**已有数据 —— 
  更新语义应由报文里的 `sjtbzt = U` 表达，而不是靠重推覆盖。
- 老平台侧遇到重复 `lsh` 的真实行为尚未联调确认，见[联调阻塞项](09-联调阻塞项.md)。

## 为什么用 JSON 列存 payload

- 18 个接口字段差异极大（1 ~ 35 个字段），逐接口建表会让表数量爆炸且难以随源文档演进；
- 保留原始 JSON 便于回溯「调用者到底发了什么」；
- MySQL 8 支持 JSON 函数，需要时可以直接查询；
- 规范化到明细表的工作可以等某个业务类别**正式接管**时再做，那时字段语义才真正确定。

## 运维查询

```sql
-- 最近的状态分布
SELECT status, COUNT(*) FROM docking_request_record GROUP BY status;

-- 某次请求的完整链路
SELECT * FROM docking_request_record WHERE record_id = '<id>';
SELECT * FROM docking_data_item   WHERE record_id = '<id>' ORDER BY item_index;

-- 按业务标签与流水号定位
SELECT * FROM docking_data_item WHERE tag = 'ycrqqy_realtime' AND lsh = '<lsh>';

-- 排查"结果未知"的请求
SELECT record_id, access_key, tag, message, received_at
FROM docking_request_record WHERE status = 'UNKNOWN' ORDER BY received_at DESC;
```
