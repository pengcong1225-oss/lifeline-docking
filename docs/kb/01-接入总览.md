# 接入总览

## 调用模型

调用者（企业）把数据推送到平台，全过程只有两个 HTTP 端点：

```text
① 取令牌
   POST /data-docking-api/token
   入参：accessKey + 秒级 timestamp + signature(HMAC-SHA256)
   出参：token

② 推数据
   POST /data-docking-api/execute/api
   Header：Authorization: Bearer <token>
   Body  ：{ apiCmd, apiBody: { tag, operationType?, data: [ ... ] } }
   出参：{ code, msg, error, data }
```

**18 个业务操作共用第 ② 个 URL**，靠请求体里的字段区分，不能只看路径。详见[路由规则与陷阱](03-路由规则与陷阱.md)。

## 签名

签名原文为 `key=value&key=value` 形式，用平台分配的 `secretKey` 计算 **HMAC-SHA256**。

> **阻塞项**：源文档没有写参数顺序、字符编码、签名输出格式（hex 大小写）和时间戳容差。
> 实现里提供 `sorted`（按参数名升序）和 `given`（文档书写顺序）两种策略，联调时用真实样本确定。
> 见 [09-联调阻塞项](09-联调阻塞项.md)。

## 成功判定

这是最容易出错的地方：

| 现象 | 是否算成功 |
| --- | :---: |
| HTTP 200 | **否** |
| HTTP 200 且 `data = true` | **否** |
| 响应体 `code = 0` | **是** |
| 响应体 `code = 1` | 否 |

**只有业务码 `code=0` 才算成功。** HTTP 状态码只代表传输层是否正常。

典型响应：

```json
{ "code": 0, "msg": "成功", "error": null, "data": true }
```

## 数据同步状态

几乎所有接口都有必填字段 `sjtbzt`（数据同步状态），取值：

| 值 | 含义 |
| --- | --- |
| `I` | 新增 |
| `U` | 更新 |
| `D` | 删除 |

注意这与 `apiBody.operationType`（部分接口用 `I`/`D` 表示批量操作类型）是**两套不同的机制**，
不要混淆。详见[公共字段约定](04-公共字段约定.md)。

## 实时数据与其他数据的差别

源文档明确：

- **实时监测数据只新增**（不更新、不删除）；
- **其他接口按流水号 `lsh` 做唯一校验**，推送方必须保证流水号唯一。

## 常见误区

1. **把 18 个接口当成 18 个 URL** —— 实际只有一个 `/execute/api`，路由靠报文内容。
2. **用 HTTP 200 判断成功** —— 必须看 `code`。
3. **把 `apiCmd` 拼写"修正"** —— `lifeline_data_batch_acces` 少一个 s 是原文，改了会路由失败。
4. **token 重复拼 `Bearer `** —— 源文档示例令牌自带 `Bearer ` 前缀，需要确认调用方是否会再拼一次。
5. **以为令牌能互认** —— 新平台签发的是自己的令牌，老平台令牌不会返回给调用者。
