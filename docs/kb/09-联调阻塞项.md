# 联调阻塞项

源文档**不足以**支撑「只改地址就能生产兼容」的承诺。以下事项必须在真实联调中确认，
**在确认之前不要当作既定事实**，也不要据此对外承诺。

## 一、必须确认的六项

### 1. 签名细节 ⚠️ 最高优先级

| 项目 | 源文档 | 影响 |
| --- | --- | --- |
| 参数顺序 | 只写 `key=value&key=value` | 顺序不同 → 签名不同 → 调用者取不到令牌 |
| 字符编码 | 未写 | UTF-8 / GBK 会算出不同结果 |
| 输出格式 | 未写 | hex 大写还是小写、是否 Base64 |
| 时间戳容差 | 未写 | 容差过严会导致正常请求被拒 |

**验证办法**：拿一组真实但安全提供的测试凭证 + 一份现有客户端的成功取令牌请求
（含明文签名原文与签名值），或官方签名测试向量，对照正反例验签。

**当前实现**：提供两种策略开关，联调时切换比对：

```yaml
lifeline:
  signature:
    param-order: sorted   # 按参数名升序；改为 given 则按文档书写顺序 accessKey,timestamp
```

### 2. `/token` 参数位置

| 来源 | 说法 |
| --- | --- |
| 接口页 | `accessKey`/`timestamp`/`signature` 为 **query** 参数，请求体 `none` |
| 接入说明 | **multipart/form-data** |

**当前实现**：新平台对外**两者都接受**；对内转发老平台时用 `token-param-style` 切换。
但必须先观察现有调用者**实际怎么发**，以及老平台实际支持哪种。

### 3. `/token` 响应格式

| 来源 | 说法 |
| --- | --- |
| 接口页 | 200 响应 Schema 与示例都是空对象 `{}` |
| 接入说明 | `data.token` / `data.issuedAt` / `data.expiresAt` |
| 示例令牌 | 自带 `Bearer ` 前缀 |
| 时间字段 | 样例是 ISO 字符串，但表述称「秒」 |

**风险**：调用者若把返回的 token 直接塞进 `Authorization`，而 token 自带 `Bearer `，
就会变成 `Bearer Bearer xxx`。

**当前实现**：新平台返回接入说明的结构，令牌**不含** `Bearer `；
解析老平台令牌时会主动剥离 `Bearer ` 前缀。

**验证办法**：取得老平台真实成功/失败响应的脱敏样本，核对调用者的解析行为。

### 4. 测试凭证

分享文档**没有提供任何可用的业务 `accessKey/secretKey`**。

> 分享文档的访问密码（`sskj-smx-rqqy`）是**文档密码，不是接口调用凭证**，不能替代。

**需要**：通过安全渠道取得测试凭证；登记时应调用老平台 `/token` 验证。
密钥只加密保存，**不得写入日志、工单、聊天或交接文档**。

**当前状态**：仓库内不含任何真实凭证；`mock-ak-0001/mock-sk-0001` 只是本机模拟器的测试值。

### 5. 业务语义

| 未定义项 | 影响 |
| --- | --- |
| 批量大小上限 | 一次能推多少条 `data[]` 未知 |
| 部分成功 | 一批里部分数据校验失败时，是整体回滚还是部分入库？返回什么？ |
| 删除/更新语义 | `operationType=D` 是物理删除还是逻辑删除？`sjtbzt=U` 的匹配键是什么？ |
| `lsh` 冲突行为 | 重复流水号是老平台报错、静默忽略还是覆盖？ |
| 实时数据 | 文档说"只新增"，但重复推送的行为未定义 |

**当前策略**：第一版**原样转发**，由老平台判定；本地按 `(tag, lsh)` 唯一键跳过重复、只计数不覆盖。

### 6. 字段类型矛盾

源文档个别字段的声明类型与语义/示例不一致：

| 字段 | 文档声明 | 矛盾点 |
| --- | --- | --- |
| `jcsj` | `integer`，说明「格式 int32」 | 语义是**毫秒时间戳**，远超 int32 范围 |
| `enterpriseUserId`、`orgId`、`receiveDate` | `object` | 无任何结构说明与示例，无法构造 |
| 部分编码字段 | `string` | 示例写成数字 |

**验证办法**：以平台实际校验结果为准；这些字段的预填值都是占位，
**不要直接当真实数据发送**。

## 二、已确认的文档冲突

### 条目 4 与条目 18 路由键重复

```text
inspection_third_party_data_access / risk / I
```

| 条目 | 源文档归类 | 字段列表 |
| ---: | --- | --- |
| 4 | 宜昌市燃气企业数据 / **用户信息** / 保存或更新 | 12 个字段（隐患模型） |
| 18 | 宜昌市燃气企业数据 / **第三方巡检隐患管理** / 保存或更新 | **完全相同的 12 个字段** |

条目 4 归在「用户信息」下，请求模型却是隐患 `risk`，与条目 18 完全重合。
源文档没有说明区别。

**待确认**：条目 4 是文档归类错误，还是确实存在第二条 `risk` 通道？

**影响**：按路由键分发时**无法区分**这两类数据。若平台方确认二者是同一接口，
可合并处理；若不同，则路由维度不足，需要补充区分手段。

代码中已固化为单元测试提醒。

## 三、建议的联调顺序

```text
① 连通性
   确认测试环境可达、令牌参数格式、签名规则
        ↓
② 令牌兼容
   用真实凭证跑通取令牌，拿到真实成功/失败响应样本
        ↓
③ 单条推送
   选字段少的接口（如 seq 15 district/D，仅 1 个字段）推一条，核对 code 与响应结构
        ↓
④ 幂等验证
   同一条数据重复推送，观察 lsh 冲突行为
        ↓
⑤ 基础数据先行
   按依赖顺序：点位 → 设备 → 巡检人员/片区 → 再推监测、报警、隐患及处置、供气量
        ↓
⑥ 批量与边界
   逐步加大批量条数，确认上限与部分成功行为
```

**依赖顺序与批量上限源文档未明确，需平台方确认后再定。**

## 四、当前不能承诺的事

- ❌ 「只改地址就能生产兼容」—— 签名与令牌格式未验证前不成立
- ❌ 全部 18 个接口可用 —— 字段语义未逐类核对
- ❌ 新平台可独立判定业务成功 —— 第一版全部依赖老平台 `code=0`
- ❌ 生产可用 —— `/admin/**` 无鉴权、令牌存内存、无部署方案

## 五、安全红线

1. 不要向老平台业务接口发送测试数据，除非已获得测试环境与明确授权；
   默认用 `tools/mock-old-platform.mjs` 验证。
2. `secretKey` 不写入日志、工单、Git、聊天或文档。
3. 生产环境不得未经网络安全评估直接沿用明文 HTTP 测试地址。
4. 生产必须关闭 `lifeline.debug.enabled`，并给 `/admin/**` 加鉴权。
