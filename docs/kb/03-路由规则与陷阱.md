# 路由规则与陷阱

## 只有两个 apiCmd

18 个业务操作全部落在两个固定 `apiCmd` 下：

| apiCmd | 用途 |
| --- | --- |
| `lifeline_data_batch_acces` | 生命线数据批量接入（施工、隐患、点位、设备、实时、报警、供气量） |
| `inspection_third_party_data_access` | 第三方巡检数据接入（巡检人员、片区、轨迹、隐患） |

> ⚠️ `lifeline_data_batch_acces` **少一个 s**，源文档原文如此。不要改成 `access`。
> 代码里有单元测试锁定这个拼写。

## 三级路由键

```text
apiCmd  +  apiBody.tag  +  apiBody.operationType(可选)
   │            │                    │
   │            │                    └─ 同一 tag 下的不同操作（I=保存或更新，D=删除）
   │            └─ 数据标签，标识业务对象
   └─ 固定指令，分两大来源
```

实际路由判定顺序：

1. 先用 `apiCmd` 区分「生命线批量」还是「第三方巡检」；
2. 再用 `tag` 定位具体业务对象；
3. 若该 `tag` 同时存在 `I` 和 `D` 两种操作，**必须再看 `operationType`**。

典型需要 `operationType` 才能区分的例子：

| tag | operationType | 含义 |
| --- | :---: | --- |
| `inspector` | `I` | 第三方巡检人员 保存或更新（8 字段） |
| `inspector` | `D` | 第三方巡检人员 删除（2 字段） |
| `district` | `I` | 第三方巡检片区 保存或更新（4 字段） |
| `district` | `D` | 第三方巡检片区 删除（1 字段） |

单看 `tag` 无法区分上面两组，字段数量都不一样，混用会直接把删除请求发成保存。

## ⚠️ 已知的重复路由冲突

**条目 4 和条目 18 的路由键完全相同**：

```text
inspection_third_party_data_access / risk / I
```

| 条目 | 源文档归类 | 请求模型 |
| ---: | --- | --- |
| 4 | 宜昌市燃气企业数据 / **用户信息** / 【批量操作】保存或更新 | `risk`（隐患），12 字段 |
| 18 | 宜昌市燃气企业数据 / **第三方巡检隐患管理** / 【批量操作】保存或更新 | `risk`（隐患），12 字段 |

一个是「用户信息」，请求模型却是隐患 `risk`，且与条目 18 高度重合。源文档没有说明区别。

**影响**：按路由键分发时无法区分这两类数据，必须向平台方确认条目 4 的真实用途
（是文档归类错误，还是确有第二个 `risk` 通道）。

代码中已把该冲突固化为单元测试（`ApiCatalogTest.duplicateRiskRouteIsAKnownDocumentationConflict`），
避免有人误以为可以靠路由键区分。

## 路由不能只看 URL

无论推哪个业务，HTTP 方法和路径都一样：

```text
POST /data-docking-api/execute/api
```

所以：

- 网关、日志、监控**不能按 URL 做统计或分流**，必须解析 `apiCmd` + `tag`；
- 接口文档工具（如 Apifox）的 OpenAPI 汇总导出会**只保留共用路径下的一份定义**，
  不能代替逐接口的字段明细；
- 本项目的[接口清单](02-接口清单.md)是逐条提取的，保留了全部 18 条。

## 相关：请求体结构

```json
{
  "apiCmd": "lifeline_data_batch_acces",
  "apiBody": {
    "tag": "ycrqqy_realtime",
    "operationType": "I",
    "data": [ { "lsh": "...", "dsbm": "420500", "..." : "..." } ]
  }
}
```

并非每个接口都有 `operationType`，也并非每个接口都要求 `apiBody` 本身必填，
实际以对应接口的 Schema 为准（见[接口清单](02-接口清单.md)）。
