接入总览

调用模型

调用者（企业）把数据推送到平台，全过程只有两个 HTTP 端点：

① 取令牌
   POST /data-docking-api/token
   入参：accessKey + 秒级 timestamp + signature(HMAC-SHA256)
   出参：token

② 推数据
   POST /data-docking-api/execute/api
   Header：Authorization: Bearer <token>
   Body  ：{ apiCmd, apiBody: { tag, operationType?, data: [ ... ] } }
   出参：{ code, msg, error, data }

18 个业务操作共用第 ② 个 URL，靠请求体里的字段区分，不能只看路径。详见路由规则与陷阱。

签名

签名原文为 key=value&key=value 形式，用平台分配的 secretKey 计算 HMAC-SHA256。

阻塞项：源文档没有写参数顺序、字符编码、签名输出格式（hex 大小写）和时间戳容差。 实现里提供 sorted（按参数名升序）和 given（文档书写顺序）两种策略，联调时用真实样本确定。 见 09-联调阻塞项。

成功判定

这是最容易出错的地方：

现象是否算成功
HTTP 200否
HTTP 200 且 data = true否
响应体 code = 0是
响应体 code = 1否

只有业务码 code=0 才算成功。 HTTP 状态码只代表传输层是否正常。

典型响应：

{ "code": 0, "msg": "成功", "error": null, "data": true }

数据同步状态

几乎所有接口都有必填字段 sjtbzt（数据同步状态），取值：

值含义
I新增
U更新
D删除

注意这与 apiBody.operationType（部分接口用 I/D 表示批量操作类型）是两套不同的机制， 不要混淆。详见公共字段约定。

实时数据与其他数据的差别

源文档明确：

  • 实时监测数据只新增（不更新、不删除）；
  • 其他接口按流水号 lsh 做唯一校验，推送方必须保证流水号唯一。

常见误区

  1. 把 18 个接口当成 18 个 URL —— 实际只有一个 /execute/api，路由靠报文内容。
  2. 用 HTTP 200 判断成功 —— 必须看 code。
  3. 把 apiCmd 拼写"修正" —— lifeline_data_batch_acces 少一个 s 是原文，改了会路由失败。
  4. token 重复拼 Bearer —— 源文档示例令牌自带 Bearer 前缀，需要确认调用方是否会再拼一次。
  5. 以为令牌能互认 —— 新平台签发的是自己的令牌，老平台令牌不会返回给调用者。

路由规则与陷阱

只有两个 apiCmd

18 个业务操作全部落在两个固定 apiCmd 下：

apiCmd用途
lifeline_data_batch_acces生命线数据批量接入（施工、隐患、点位、设备、实时、报警、供气量）
inspection_third_party_data_access第三方巡检数据接入（巡检人员、片区、轨迹、隐患）

⚠️ lifeline_data_batch_acces 少一个 s，源文档原文如此。不要改成 access。 代码里有单元测试锁定这个拼写。

三级路由键

apiCmd  +  apiBody.tag  +  apiBody.operationType(可选)
   │            │                    │
   │            │                    └─ 同一 tag 下的不同操作（I=保存或更新，D=删除）
   │            └─ 数据标签，标识业务对象
   └─ 固定指令，分两大来源

实际路由判定顺序：

  1. 先用 apiCmd 区分「生命线批量」还是「第三方巡检」；
  2. 再用 tag 定位具体业务对象；
  3. 若该 tag 同时存在 I 和 D 两种操作，必须再看 operationType。

典型需要 operationType 才能区分的例子：

tagoperationType含义
inspectorI第三方巡检人员 保存或更新（8 字段）
inspectorD第三方巡检人员 删除（2 字段）
districtI第三方巡检片区 保存或更新（4 字段）
districtD第三方巡检片区 删除（1 字段）

单看 tag 无法区分上面两组，字段数量都不一样，混用会直接把删除请求发成保存。

⚠️ 已知的重复路由冲突

条目 4 和条目 18 的路由键完全相同：

inspection_third_party_data_access / risk / I
条目源文档归类请求模型
4宜昌市燃气企业数据 / 用户信息 / 【批量操作】保存或更新risk（隐患），12 字段
18宜昌市燃气企业数据 / 第三方巡检隐患管理 / 【批量操作】保存或更新risk（隐患），12 字段

一个是「用户信息」，请求模型却是隐患 risk，且与条目 18 高度重合。源文档没有说明区别。

影响：按路由键分发时无法区分这两类数据，必须向平台方确认条目 4 的真实用途 （是文档归类错误，还是确有第二个 risk 通道）。

代码中已把该冲突固化为单元测试（ApiCatalogTest.duplicateRiskRouteIsAKnownDocumentationConflict）， 避免有人误以为可以靠路由键区分。

路由不能只看 URL

无论推哪个业务，HTTP 方法和路径都一样：

POST /data-docking-api/execute/api

所以：

  • 网关、日志、监控不能按 URL 做统计或分流，必须解析 apiCmd + tag；
  • 接口文档工具（如 Apifox）的 OpenAPI 汇总导出会只保留共用路径下的一份定义， 不能代替逐接口的字段明细；
  • 本项目的接口清单是逐条提取的，保留了全部 18 条。

相关：请求体结构

{
  "apiCmd": "lifeline_data_batch_acces",
  "apiBody": {
    "tag": "ycrqqy_realtime",
    "operationType": "I",
    "data": [ { "lsh": "...", "dsbm": "420500", "..." : "..." } ]
  }
}

并非每个接口都有 operationType，也并非每个接口都要求 apiBody 本身必填， 实际以对应接口的 Schema 为准（见接口清单）。

新平台（本项目 lifeline-docking）是数据上收开放平台，用来逐步替换老平台。 过渡期核心约束只有一条：

调用者只替换接口地址。 继续使用老平台分配的 accessKey/secretKey、原请求路径、 原请求字段、原调用方式，不改鉴权代码、不改业务代码。

两条独立的迁移线

迁移线第一天的状态终态
鉴权迁移新平台独立对外验签、签发自己的令牌；内部访问老平台时仍用该调用者的老凭证取老令牌不再需要老平台令牌
业务迁移老平台是业务成功判定方；新平台逐类实现、影子比对、切换新平台自行处理全部业务

不要混淆：鉴权从第一天就切到新平台，业务则是逐类切换的。

数据流

① 登记（一次性）
   企业 → 提交老平台 accessKey/secretKey → AES-256-GCM 加密入库

② 取令牌
   调用者 → POST /data-docking-api/token
          → 新平台按兼容规则验签
          → 签发【新平台自己的】令牌，老平台令牌不返回

③ 推数据
   调用者 → POST /data-docking-api/execute/api  (Bearer 新令牌)
          → 验令牌、识别调用者
          → 可靠留存原始请求（失败则绝不转发）
          → 数据项按 lsh 判重入库
          → 按 apiCmd + tag + operationType 路由
              ├─ 已接管：新平台自行处理
              └─ 未接管：用该调用者老凭证取老令牌 → 同步转发老平台
                        老平台 code=0 才算成功

令牌的双层设计

调用者 ──新平台令牌──> 新平台 ──老平台令牌──> 老平台
         (对外签发)              (内部获取，绝不外泄)
  • 新平台令牌：新平台自己签发，调用者用它访问新平台。
  • 老平台令牌：新平台用调用者的老凭证在内部换取，仅用于转发，不返回给调用者。

两者不要求互认，调用者也不需要维护两套令牌。

老平台业务接口要求 Authorization: Bearer <token>，所以「用调用者原凭证转发」 在技术上仍然包含内部获取老令牌 —— 不能把 accessKey/secretKey 直接当业务接口的令牌用。

请求状态机

状态含义对调用者的响应
RECEIVED已可靠留存，尚未转发—
ACCEPTED_OLD老平台返回 code=0业务 code=0（HTTP 200）
REJECTED_OLD老平台返回非零业务码业务 code=1（HTTP 200）
REJECTED_LOCAL新平台自身拒绝（报文非法、路由缺字段、留存失败）业务 code=1（HTTP 400）
UNKNOWN老平台超时或断线，结果未知业务 code=1（HTTP 502）

为什么把 UNKNOWN 单独拎出来

老平台超时或断线时，数据可能已经写入老平台，也可能没有。此时：

  • 不能报成功 —— 调用者会以为数据已接收；
  • 不能报失败让调用者盲目重推 —— 可能造成重复数据；
  • 不能自动重放 —— 老平台幂等性尚未验证。

所以对外明确返回 502 + code=1，语义是「未确认，请人工核对」。 这是第一版刻意不做自动重试的原因。

逐类接管

RouteRegistry 维护「已由新平台接管」的路由键集合，第一版为空： 所有业务都转发老平台，由老平台判定成功。

切换某类业务的判断依据（缺一不可）：

  1. 字段含义与必填规则已逐字段核对；
  2. 成功/失败判定与老平台一致；
  3. 重复提交、流水号冲突行为已确认；
  4. 历史数据迁移与对账方案就绪；
  5. 有可回退的开关（RouteRegistry 支持 rollback）。

试点建议：先挑有明确唯一键、数据量适中、依赖少的类别； 实时监测和带更新/删除顺序的类别后移。

三张表

docking_caller_credential   企业登记的老凭证（密钥密文）
        │ accessKey
        ▼
docking_request_record      每次业务请求的留存信封（原始报文 + 状态 + 老平台响应）
        │ record_id
        ▼
docking_data_item           逐条业务数据项（判重、可查询）

1. docking_caller_credential —— 调用者凭证

字段说明
access_key老平台分配的 accessKey，唯一键
secret_ciphersecretKey 密文：Base64(iv(12) || ciphertext+tag)，AES-256-GCM
secret_hint密钥尾号（如 ****0001），仅用于人工识别，不可回推密钥
company_name / contact企业信息，便于运营识别
enabled1=启用 0=停用；停用后无法取令牌
verified_at / verify_message最近一次向老平台验证凭证的结果

设计要点

  • 只存密文。任何接口响应、日志、工单都不出现明文或密文。
  • 主密钥来自 LIFELINE_MASTER_KEY；更换或丢失主密钥会导致已登记密钥全部无法解密。
  • 更新凭证时 accessKey 不允许改（接口层面已限制），避免与已发放令牌的归属错位。

2. docking_request_record —— 请求留存

字段说明
record_id留存 ID（UUID），主键
access_key调用者
api_cmd / tag / operation_type路由键三要素
data_count报文里 data[] 的条数
stored_count实际入库条数
duplicate_count因 lsh 重复被跳过（未覆盖）的条数
raw_body原始请求体，原样保存
status见状态机
message处理说明
old_platform_code老平台业务码；NULL 表示未取得（转发失败或未转发）
old_response老平台原始响应，排障时最关键的一列
sourceAPI=调用者推送，DEBUG=调试台
received_at / forwarded_at接收与转发完成时间

设计要点

  • 先留存再转发。留存与数据项入库在同一事务内完成（RecordPersister）； 留存失败直接返回失败，绝不转发。
  • 保留 raw_body 原文而不只存解析结果，便于事后对账与复现。
  • 索引：received_at（按时间查）、(api_cmd, tag, operation_type)（按业务查）、 status（按状态筛）、access_key（按调用者查）。

3. docking_data_item —— 上收数据项

字段说明
record_id所属留存记录
api_cmd / tag / operation_type冗余存一份，便于脱离信封独立查询
item_index在 data[] 中的原始下标
lsh流水号，可空
payload原始数据项 JSON

判重策略

UNIQUE KEY uk_tag_lsh (tag, lsh)
  • 源文档要求「按流水号做唯一校验」，所以对 (tag, lsh) 建唯一键。
  • lsh 允许 NULL：第三方巡检族的接口没有 lsh， MySQL 唯一键允许多个 NULL，因此这些接口的数据不会被误判重复。
  • 重复时跳过插入并计数（duplicate_count），不覆盖已有数据 —— 更新语义应由报文里的 sjtbzt = U 表达，而不是靠重推覆盖。
  • 老平台侧遇到重复 lsh 的真实行为尚未联调确认，见联调阻塞项。

为什么用 JSON 列存 payload

  • 18 个接口字段差异极大（1 ~ 35 个字段），逐接口建表会让表数量爆炸且难以随源文档演进；
  • 保留原始 JSON 便于回溯「调用者到底发了什么」；
  • MySQL 8 支持 JSON 函数，需要时可以直接查询；
  • 规范化到明细表的工作可以等某个业务类别正式接管时再做，那时字段语义才真正确定。

运维查询

-- 最近的状态分布

-- 某次请求的完整链路

联调阻塞项

源文档不足以支撑「只改地址就能生产兼容」的承诺。以下事项必须在真实联调中确认， 在确认之前不要当作既定事实，也不要据此对外承诺。

一、必须确认的六项

1. 签名细节 ⚠️ 最高优先级

项目源文档影响
参数顺序只写 key=value&key=value顺序不同 → 签名不同 → 调用者取不到令牌
字符编码未写UTF-8 / GBK 会算出不同结果
输出格式未写hex 大写还是小写、是否 Base64
时间戳容差未写容差过严会导致正常请求被拒

验证办法：拿一组真实但安全提供的测试凭证 + 一份现有客户端的成功取令牌请求 （含明文签名原文与签名值），或官方签名测试向量，对照正反例验签。

当前实现：提供两种策略开关，联调时切换比对：

lifeline:
  signature:
    param-order: sorted   # 按参数名升序；改为 given 则按文档书写顺序 accessKey,timestamp

2. /token 参数位置

来源说法
接口页accessKey/timestamp/signature 为 query 参数，请求体 none
接入说明multipart/form-data

当前实现：新平台对外两者都接受；对内转发老平台时用 token-param-style 切换。 但必须先观察现有调用者实际怎么发，以及老平台实际支持哪种。

3. /token 响应格式

来源说法
接口页200 响应 Schema 与示例都是空对象 {}
接入说明data.token / data.issuedAt / data.expiresAt
示例令牌自带 Bearer 前缀
时间字段样例是 ISO 字符串，但表述称「秒」

风险：调用者若把返回的 token 直接塞进 Authorization，而 token 自带 Bearer ， 就会变成 Bearer Bearer xxx。

当前实现：新平台返回接入说明的结构，令牌不含 Bearer ； 解析老平台令牌时会主动剥离 Bearer 前缀。

验证办法：取得老平台真实成功/失败响应的脱敏样本，核对调用者的解析行为。

4. 测试凭证

分享文档没有提供任何可用的业务 accessKey/secretKey。

分享文档的访问密码（sskj-smx-rqqy）是文档密码，不是接口调用凭证，不能替代。

需要：通过安全渠道取得测试凭证；登记时应调用老平台 /token 验证。 密钥只加密保存，不得写入日志、工单、聊天或交接文档。

当前状态：仓库内不含任何真实凭证；mock-ak-0001/mock-sk-0001 只是本机模拟器的测试值。

二、已确认的文档冲突

条目 4 与条目 18 路由键重复

inspection_third_party_data_access / risk / I
条目源文档归类字段列表

FAQ 与排查

对接前

Q：接入到底要改什么？

只改接口地址。继续用老平台分配的 accessKey/secretKey、原请求路径、原字段、原调用方式。

如果调用者把「令牌地址」和「业务地址」分开配置，两处都要改成新平台地址， 但不需要改鉴权代码或业务调用代码。

Q：为什么 18 个接口看起来是同一个 URL？

源平台的设计就是共用一个 POST /data-docking-api/execute/api， 靠报文体里的 apiCmd + apiBody.tag（必要时加 apiBody.operationType）区分。 详见路由规则与陷阱。

Q：我怎么知道该填哪些字段？

查接口清单找到对应条目，字段逐个列在 src/main/resources/docking-api-catalog.json 里； 也可以直接用调试台选接口，会自动生成带字段说明的报文模板。

调用时

Q：HTTP 200 了为什么还说失败？

因为成功只看响应体里的 code：

{ "code": 0, "msg": "成功", "data": true }   ← 只有这个是成功
{ "code": 1, "msg": "参数错误" }              ← HTTP 200 也是失败

Q：apiCmd 是不是写错了？acces 少一个 s。

没有错。lifeline_data_batch_acces 是源文档原文拼写，必须照抄。 改成 access 会导致路由失败。代码里有测试锁定这个值。

Q：token 前面要不要加 Bearer ？

要加：Authorization: Bearer <token>。

但要注意：如果平台返回的 token 自身已经带了 Bearer 前缀， 再拼一次会变成 Bearer Bearer xxx。这是源文档记录在案的歧义点， 新平台返回的令牌不含前缀。见阻塞项 3。

Q：operationType 和 sjtbzt 都是 I/D，有什么区别？

  • apiBody.operationType：结构层，决定路由到哪个接口（保存 or 删除）；
  • apiBody.data[].sjtbzt：数据层，表示这一条数据的同步动作（I 新增 / U 更新 / D 删除）。

两者独立，可以组合出现。

Q：lsh 怎么生成？

dsbm（地市编码）+ sjly（数据来源）+ 业务扩展标识，只允许字母数字，最长 128。 推送方必须保证唯一，平台按它做唯一校验。

Q：经纬度用什么坐标系？

CGCS2000（大地 2000），字段名 lon/jd（经度）、lat/wd（纬度）。

平台行为

Q：重复推送同一条数据会怎样？

新平台侧按 (tag, lsh) 唯一键跳过并计数，不覆盖已有数据（见上收数据页的"重"计数）。

老平台侧的行为尚未验证 —— 可能报错、忽略或覆盖，需联调确认。

Q：推送时老平台超时了，我该重推吗？

暂时不要自动重推。 此时平台返回 HTTP 502，语义是"结果未知"： 数据可能已写入老平台，也可能没有。老平台的幂等性未经验证，盲目重推可能产生重复数据。

正确做法：先在「上收数据」页按留存 ID 查这次请求的状态与老平台响应，再人工决定。

Q：数据推给新平台后，老平台还会收到吗？

会。第一版所有业务都转发给老平台，由老平台判定成功。 新平台只是在其前面加了鉴权、留存与路由层。

后续按业务类别逐步接管，接管后该类才由新平台自行处理。

运维排查

Q：怎么查某次请求到底发生了什么？

在上收数据页找到记录点「详情」，或直接查库：

SELECT raw_body, old_response, old_platform_code, status, message
FROM docking_request_record WHERE record_id = '<id>';

old_response 是老平台的原始响应，排障时最关键。

Q：状态 UNKNOWN 是什么意思？

老平台超时或断线，结果未知。平台刻意不报成功也不报失败，避免误导。 需要人工核对老平台侧是否已接收。

Q：stored_count=0 但请求成功了？

说明所有数据项的 lsh 都已存在（duplicate_count 会显示条数），属预期判重行为。

Q：启动后所有请求都失败/超时？

  1. 看 lifeline.old-platform.base-url 是否可达；
  2. 看应用日志里取令牌是否成功；
  3. 本机联调应先启动 tools/mock-old-platform.mjs 并把地址指过去。

Q：报「secretKey 解密失败」怎么办？

主密钥变了。AES-GCM 无法用新密钥解开旧密文，只能让企业重新登记凭证。

所以：LIFELINE_MASTER_KEY 必须固定保存，不要随意更换。

Q：能改 accessKey 吗？

不能。更新凭证时 accessKey 被锁定，避免与已发放的令牌归属错位。 换个 accessKey 等于换一个凭证，请新建。
